# RC17 — обновления Parallel Finder

Встроенная фоновая проверка GitHub Releases, каналы Stable/Beta, подписанные
пакеты обновления и отдельный ParallelFinderUpdater.exe. Диалог использует
существующие Theme, PfButton, PfIconButton, шрифты и переходы интерфейса.
Во время загрузки тот же диалог показывает прогресс, объём и скорость.

Автоматическая проверка включена по умолчанию, загрузка — выключена.
Автоматической установки нет: после проверки загруженного пакета необходимо
нажать «Установить и перезапустить». Незавершённые анализ и экспорт блокируют
установку. «Позже» скрывает диалог; «Пропустить эту версию» сохраняет решение.
Ручная проверка позволяет снова увидеть пропущенную версию.

## Архитектура

`updates` — самостоятельная библиотека C++23. UpdateService отвечает за
состояния, асинхронные сетевые запросы, предпочтения и передачу установки.
UpdateManifest проверяет версии, подписи, размеры, хеши и допустимые пути.
UpdateTransaction распаковывает и проверяет файлы, сохраняет локальные файлы,
ведёт журнал и выполняет активацию/откат. QML отображает состояние сервиса.

Проверка начинается через 2,5 секунды после обычного запуска и не блокирует
начальную загрузку UI. Диагностические процессы проверку не выполняют.
Предпочтения находятся в `updates/preferences.json` в пользовательском
каталоге приложения и сохраняются отдельно от параметров анализа.

Версии сравниваются по SemVer, включая числовые компоненты rc.16.4.1.
Stable исключает prerelease; Beta принимает prerelease и обычные релизы.
Релизы моделей/runtime с нечисловыми тегами не участвуют. Читаются до пяти
страниц по 100 релизов; выбирается максимальная подходящая версия.
Документация API: https://docs.github.com/en/rest/releases/releases.

## Подлинность

Каждый доступный для встроенного обновления Release должен содержать:

- `ParallelFinder-<version>-Portable-x64.zip`;
- `update.json`;
- `update.json.sig` — 64-байтовую подпись Ed25519 исходных байтов JSON.

SHA-256 архива, его размер, версия, канал, платформа, имя пакета, changelog
и полный список файлов подписаны одним манифестом. Публичный ключ встроен
в приложение и updater при сборке из `tools/release/update-public-key.pem`.
Полученный по сети публичный ключ никогда не используется вместо встроенного.
Подпись проверяется до предложения установки и повторно независимым updater.
SHA-256 каждого распакованного файла проверяется перед запуском новой версии.
Неподписанные старые Releases не устанавливаются через этот механизм.

OpenSSL выполняет однократную проверку Ed25519:
https://docs.openssl.org/3.0/man3/EVP_DigestVerifyInit/.
В production разрешены только HTTPS-запросы и перенаправления на разрешённые
хосты GitHub; отключения TLS-проверки нет. Локальный HTTP и подмена ключа
доступны только через C++-конструктор в тестах, не через QML, параметры
запуска или переменные окружения production-приложения.

При внедрении создан закрытый ключ в пользовательском каталоге
`%LOCALAPPDATA%/ParallelFinder/release-signing/update-ed25519-private.pem`.
Он не включён в Git, пакеты приложения и архив исходников. Доступ к каталогу
ограничен владельцем и SYSTEM. Владельцу проекта необходимо сохранить
его защищённую резервную копию: без него будущие пакеты нельзя подписать
для уже установленных приложений с этим ключом доверия.

`build-windows.ps1` собирает обе программы, создаёт portable ZIP, подписывает
манифест и проверяет подпись встроенным публичным ключом. Отсутствующий или
неподходящий закрытый ключ останавливает создание update-capable Release.
Путь можно передать параметром `-SigningKey`; закрытый ключ не должен
храниться в репозитории или попадать в логи. Публикация Release выполняется
отдельно владельцем проекта; создание пакета само по себе ничего не публикует.

## Установка и восстановление

Updater и необходимые DLL копируются за пределы установки в пользовательский
каталог обновлений. Перед закрытием основной программы updater должен
подтвердить свой запуск и проверку пакета; при таймауте основное приложение
остаётся открытым, а передача отменяется. Updater ждёт завершения основного процесса и не изменяет
его файлы до закрытия. Полный пакет распаковывается в соседний каталог
`<installation>.pf-stage` на том же томе. Ссылки, reparse points, обходы путей,
потоки NTFS, дубли и незаявленные файлы запрещены. Пользовательские файлы,
не входящие в новый пакет, сохраняются; для installer сохраняются unins-файлы
и существующие пути/ярлыки. Установщик Inno Setup продолжает работать отдельно.

Сначала выполняется проверочный запуск нового приложения из staging.
Затем с журналом на диске старый каталог переименовывается в `.pf-backup`,
а подготовленный — в исходный путь. Новый процесс должен подтвердить
первый показ интерфейса и точную версию. При ошибке staging, активации или
перезапуска восстанавливается предыдущий каталог; неудачный перезапуск
останавливается до отката. После успешного подтверждения удаляется резервная
копия. Ошибка очистки сохраняет её, а следующая установка отказывается
перезаписать оставшийся backup.

Это транзакционная замена полного каталога с восстановлением; Windows
не предоставляет единственной операции обмена двух каталогов. Между двумя
переименованиями есть короткий промежуток. Если процесс/питание прервутся
в этот момент, восстановление по журналу выполняется сохранённым updater
через HKCU RunOnce при следующем входе в Windows, прежде чем он перезапустит
старое приложение. RunOnce регистрируется до первой модификации установки.
При обычной ошибке откат выполняется немедленно. В случае блокировки файлов
резервная копия и журнал сохраняются; updater сообщает ошибку без QMessageBox.

Нужны права записи в установку и её родительский каталог. Текущий installer
устанавливает приложение в пользовательский каталог. Для вручную перенесённой
установки в защищённый Program Files встроенное обновление без повышения прав
откажет безопасно; автоматического запуска с повышенными правами нет.
Portable обновляется на месте, если её каталог и родитель доступны для записи.

## Проверки

`pf_update_tests` проверяет локальный Release feed и реальные подписанные
тестовые манифесты с отдельными временными ключами. Проверяются найденное
обновление, отсутствие обновлений, сетевой сбой, подмена подписи, повреждение
скачанного ZIP, отмена, каналы, пропуск версии и запрет установки до согласия.
Транзакционные проверки используют временные установки: успешная активация
с подтверждённым перезапуском, ошибки установки/перезапуска, восстановление
прерванной активации, сохранение portable-файлов и uninstaller, повреждённый
файл при правильном хеше ZIP и отказ затрагивать посторонний staging.
QML-проверка открывает настоящий UpdateDialog в Main, проверяет состояния,
прогресс и кнопки, сохраняет изображения для визуального просмотра.

Сетевые/транзакционные проверки воспроизводимы без публикации Release.
Настоящий сетевой ответ GitHub и физическое отключение питания не моделируются
как уже выполненное production-обновление. Самопроверка нового пакета и
подтверждение настоящего перезапуска также действуют в production-updater.
