## 1. D1 — Экспорт модели, батчинг, ветвление end2end/NMS

### Решение

1. Экспорт ONNX **только со статическими формами**: `dynamic=False`, фиксированный
   `imgsz=640`, фиксированный `batch`. Никаких динамических осей ни по batch, ни по
   пространству в v1.
2. Батч задаётся **файлом модели**, а не рантаймом. В релизе два профиля:
   | Профиль | batch | точность | Назначение |
   |---|---|---|---|
   | `b1` | 1 | fp32 | универсальный: CPU, DirectML, малый VRAM; дефолт |
   | `b8` | 8 | fp16 | GPU-tier «Максимум» (CUDA / TensorRT) |
3. NMS внутри графа (`nms=True`) включаем **только для архитектур, которые это
   поддерживают** (YOLO11/12-семейство). Для архитектур с нативной end2end-головой
   (YOLO26) флаг отсутствует by design, NMS уже в графе.
4. Рантайм определяет ветку постобработки **по загруженной модели**, а не по имени файла:
   приоритет 1 — `metadata_props` графа (`end2end`, `args.nms`); приоритет 2 — форма выхода:
   ранг-3 выход с последней размерностью 6 (`[B, 300, 6]`) ⇒ NMS уже в графе;
   `[B, 56, 8400]` (4 box + 1 cls + 17×3 keypoints) ⇒ NMS наш, в C++.
5. Вход всегда letterbox 640×640. Если кадров в батче меньше batch-размера файла,
   **хвост добивается повтором последнего кадра** (не нулями — нулевой кадр даёт
   ложную статистику и лишние детекции), результаты лишних слотов отбрасываются.
6. Провайдер-специфично: `b1` для CPU/DML, `b8` только для CUDA/TensorRT. Смена профиля —
   событие кэша сессий в `pfgpu` (ключ сессии = модель + провайдер + профиль).

### Обоснование

- `nms=True` + `dynamic=True` давали молчаливо неверный результат при batch > 1: валидными
  были детекции только для индекса 0 ([ultralytics#23647](https://github.com/ultralytics/ultralytics/issues/23647),
  открыт 2026-02-12, закрыт; в баг-репорте batch=8 → mAP50 падает с ~0.99 до ~0.05 при
  неизменном входе). Фикс свежий, в закреплённой версии полагаться на него нельзя.
- TensorRT EP для динамических входов требует **явных профилей min/opt/max shapes**
  (`trt_profile_min_shapes` / `trt_profile_opt_shapes` / `trt_profile_max_shapes`), а кэш
  движков при смене профиля перестраивается
  ([ORT TRT EP docs](https://onnxruntime.ai/docs/execution-providers/TensorRT-ExecutionProvider.html),
  [onnxruntime#16889](https://github.com/microsoft/onnxruntime/issues/16889): «cache is not being
  re-used with dynamic dimensions»). Это означает непредсказуемый прогрев на первом запуске у
  пользователя — прямое противоречие требованию «прогрев предсказуем».
- Статические формы дают: детерминированный прогрев, кэшируемый TRT-движок, отсутствие
  shape-inference-накладных расходов и воспроизводимые перф-метрики тиров
  Быстро/Средне/Максимум (стадия 6).
- Почему batch в файле, а не «один файл на все случаи»: при статических формах модель
  принимает ровно N изображений. Дублировать один и тот же вес в двух профилях дороже по
  трафику (x-pose ≈110 МБ fp32 / ≈55 МБ fp16), но дешевле по времени жизни: базовый
  пользователь качает только `b1`, GPU-tier — `b8`; итоговый бандл собирается по тиру (стадия 6).
- Почему fp16 только на GPU: CPU и DirectML на fp16 дают либо отсутствие поддержки, либо
  провал по скорости/точности; fp16 для TRT/CUDA — стандартная и безопасная практика.

### Что не делаем и почему

- Не пишем свои CUDA-ядра (nvcc не поддерживает GCC/MinGW host-компилятор — ТЗ п.1).
- Не используем динамические оси «на будущее» — это единственный источник недетерминизма
  в батчинге, который мы можем исключить сейчас бесплатно.
- Не зашиваем batch в C++-константу: `pfgpu` читает профиль из манифеста модели, поэтому
  добавление `b16` — это новая запись в манифесте, а не правка ядра.

### Критерий пересмотра

Возвращаемся к вопросу, если (а) фикс dynamic+NMS войдёт в закреплённую версию Ultralytics и
(б) на GPU-tier будет измерена просадка throughput >1.3× относительно `b8`. Не раньше стадии 6.

## 2. D2 — SceneDetector: метод и пороги

### Решение

Реализация своя, в `pfcore` (Qt-free, без Python/OpenCV), по мотивам ContentDetector +
AdaptiveDetector из PySceneDetect — это не копия библиотеки, а два хорошо описанных численных
критерия, которые нам нужны по отдельности для настройки порога:

- Кадр уменьшается до **128×72** (`sws_scale` существующим FFmpeg-конвейером), переводится в
  HSV. Считается взвешенная дельта к предыдущему кадру: **веса H/S/V = 1.0/1.0/1.0, edges = 0.0**
  (дефолт `Components` PySceneDetect).
- Граница ставится по **двум критериям одновременно**: абсолютный порог и адаптивный
  (скользящее среднее по окну ±2 кадра с множителем). Адаптивный критерий нужен именно
  под наш контент: быстрая камера/драка даёт всплески дельты, которые абсолютный порог
  ловит как ложные склейки.
- Дефолты (все — в `settings.json`, доступны в Settings-диалоге):

  | Параметр | Дефолт | Диапазон | Источник дефолта |
  |---|---|---|---|
  | `contentThreshold` (абсолютный, шкала 0–255) | 27.0 | 8–60 | дефолт `ContentDetector.threshold` |
  | `adaptiveMultiplier` | 3.0 | 1.5–8.0 | дефолт `AdaptiveDetector.adaptive_threshold` |
  | `adaptiveWindow` (кадров до/после) | 2 | 1–5 | дефолт `AdaptiveDetector.window_width` |
  | `minContentVal` | 15.0 | 5–40 | дефолт `AdaptiveDetector.min_content_val` |
  | `minSceneLen` (кадров) | **8** | 4–60 | **изменено** с 15 (см. ниже) |
  | `fadeThreshold` (средняя яркость 0–255) | 12 | 5–30 | дефолт `ThresholdDetector.threshold` |
  | `dissolveAccumRatio` | 0.40 | 0.2–0.8 | наше решение, калибруется на фикстуре |

- `minSceneLen` снижен с дефолтных 15 до **8 кадров** осознанно: приложение работает по
  экшн-материалу (скриншоты прототипа — фильм/постановочные сцены), где вставки короче
  0.5 с — норма; 15 кадров при 30 fps склеивают такие вставки с соседним планом и ломают
  границу клипа. Риск ложных границ компенсирован адаптивным критерием. Значение
  перепроверяется на видеофикстурах в стадии 2b.
- **Медленные переходы — отдельный проход, а не игнор:** fade in/out из чёрного ловится по
  средней яркости (`fadeThreshold`), диссолв — по накоплению дельты выше
  `dissolveAccumRatio × contentThreshold` на протяжении ≥ 3 кадров. Граница ставится в середину
  перехода. Причина: ТЗ п.3 определяет клип как «от первого появления персонажа до конца сцены»,
  и диссолв, разрезанный как два плана, даёт два неверных результата вместо одного верного.
- Сцены короче минимального окна движения (0.5 с, см. раздел 8) остаются в списке сцен и на
  таймлайне, но не становятся кандидатами на параллель — окно движения в них физически не
  помещается.

### Почему не чужие готовые средства

- `ffmpeg -vf select='gt(scene,...)'` даёт только пороговое решение и не отдаёт нам
  покадровую дельту; настройку порога и адаптивный критерий в нём не выразить, а
  диагностику ложных склеек мы теряем. Кроме того, это отдельный процесс на каждый файл
  поверх уже имеющегося декодера.
- PySceneDetect — Python-зависимость, в поставку не входит (ТЗ п.1). Берём метод и дефолты,
  не библиотеку.

### Критерий приёмки (стадия 2b)

- Синтетическая фикстура: 8 склеенных клипов с известными границами → точность границ ±1 кадр,
  precision и recall ≥ 0.95.
- Реальный видеофикстур: зафиксированные границы в `expected.json`, регресс-тест; пороги
  меняются только вместе с обновлением ожидаемых значений в том же коммите.
- Память O(1) по кадрам (предыдущий кадр + кольцевой буфер адаптивного окна), декодирование
  отдельным проходом по файлу, не мешает конвейеру pose-инференса.

## 3. D3 — Тай-брейк доминантного персонажа

Метрика: суммарное время в кадре = число кадров, где трек присутствует (эквивалентно времени
при постоянном fps; для VFR считаем по длительностям кадров).

Ничья фиксируется при разнице времени ≤ `max(5 кадров, 2% длительности файла)` — жёсткое
равенство не встречается на практике, а произвольный «перевес в 1 кадр» давал бы нестабильный
выбор при повторных прогонах и «дрожащие» F1-фикстуры.

Каскад разрешения ничьей (строго детерминированный, порядок — часть контракта):

1. больше кадров в кадре;
2. больше средняя площадь bounding box, нормированная на площадь кадра — «ближе к камере»
   (кандидат из ТЗ). Нормировка обязательна: файлы бывают разных разрешений и кропов,
   абсолютная площадь их несравнима;
3. выше средняя уверенность keypoints по кадрам присутствия (более надёжный трек);
4. более раннее первое появление в файле;
5. меньший `trackId`.

Пункты 4–5 нужны не для качества, а для воспроизводимости: при ничьей по всем метрикам
результат не должен зависеть от порядка обхода хэш-таблиц треков.

Дополнительно перед выбором доминанта: фрагментированные треки одного человека склеиваются,
если они не пересекаются во времени, разрыв ≤ 0.5 с и IoU граничных боксов ≥ 0.3 (артефакт
пропущенной детекции). Без этого «доминант» может оказаться половиной персонажа, а
дескрипторы получат дырку.

## 4. D4 — Appearance-компонент: честное исключение + veto-фильтр

### Решение

**Формула сходства v1 — без appearance-компоненты:**

```
S_motion = clamp(1 − D_norm / D_ref, 0, 1)
S_time   = 1 − min(1, |dur_A − dur_B| / max(dur_A, dur_B))
S        = (1 − timeWeight) · S_motion + timeWeight · S_time
```

- `D_norm` — стоимость пути DTW с полосой Сакое-Чиба, делённая на число шагов пути; считается
  на keypoints, центрированных по корню (таз/центр бёдер) и нормированных на длину корпуса
  (плечи↔бёдра), с вычитанием оценённого шумового пола (слайдер «коэффициент шума», D7).
- При включённой опции «Зеркальные позы» (дефолт — вкл, как в прототипе) берётся
  `max(S_normal, S_mirrored)`.
- `D_ref` — **калибровочная константа, начальное значение 0.35** нормированных единиц корпуса;
  финальное значение фиксируется в стадии 3b по фикстурам и записывается в этот документ.
- Веса частей тела (опция прототипа) в v1 влияют только на `D_norm` внутри `S_motion`,
  отдельного компонента не добавляют.

**Appearance в скор не входит вообще.** Pose-модель не отдаёт embedding внешности; чтобы
получить его, нужна вторая модель (Re-ID), а это ещё один вес, ещё один профиль провайдера и
ещё один источник расхождений между GPU-tier. Исключаем компонент из формулы **явно** — это
решение, а не пропущенная часть.

**Вместо этого — appearance-gate как veto (не вклад в скор):** по кадрам окна считается
усреднённая HSV-гистограмма внутри bbox персоны (H 12 × S 4 бина), сравнивается через
histogram intersection с партнёрской. Если пересечение < `appearanceGateThreshold` — пара
отбрасывается. Дефолт: **включён, порог 0.55**, живёт в опциях (не среди 9 слайдеров).

### Обоснование и как снимается неопределённость

- Без любого фильтра pipeline сравнивает доминанта файла A с доминантом файла B; если это
  разные люди с похожей пластикой, пара пройдёт по движению — precision падает на самом
  частом сценарии использования (два разных материала).
- Гистограмма по bbox — это не Re-ID: она переживает разное освещение хуже, чем обученный
  embedding, и ломается на смене костюма. Поэтому дефолт 0.55 намеренно мягкий, и порог
  живёт в опциях с тултипом «при ложных парах уменьшайте, при пропусках — увеличивайте».
- Честный способ зафиксировать дефолт: в стадии 3b F1 считается в двух конфигурациях
  (gate ON / OFF) на общих фикстурах. Если ΔF1 (ON − OFF) < 0 — дефолт переключается на OFF,
  и таблица выше правится в том же коммите.
- Re-ID-модель (отдельный embedding) — кандидат на отдельную задачу **после** 3b: решение
  принимается по измеренному узкому месту precision, а не заранее.

## 5. D5 — Откуда конечный пользователь берёт .onnx

### Порядок поиска модели (ModelStore, `pfservices`)

1. `<exe>/models/<profile>.onnx` — портативный/офлайн режим: пользователь положил сам, или
   бандл собран вместе с моделью (стадия 6). Ничего не качается.
2. `%LocalAppData%\ParallelFinder\models\<profile>.onnx` — основной путь после автозагрузки.
3. Загрузка с **GitHub Releases проекта** по описанию из `models/manifest.json` (в репозитории,
   не в C++): имя профиля, размер, SHA-256, URL, лицензия, минимальная версия приложения.

Загрузка: HTTPS, докачка через `Range`, запись в `*.part`, проверка размера и SHA-256 **до**
атомарного переименования в рабочее имя. Прогресс и текущая стадия («Загружаем модель
распознавания поз…», проценты) идут в Splash-оверлей — как в прототипе, чтобы первый запуск
не выглядел зависшим. Автозагрузку можно выключить в настройках.

Если модель не найдена и сети нет — Splash показывает понятное состояние с кнопками
«Указать файл .onnx…» (файловый диалог, результат сохраняется в настройках) и «Повторить».
Молчаливого падения на старте нет.

### Почему так

- Никакого Python/`vpk` в поставке (ТЗ п.1), значит логика получения весов обязана жить в C++;
  TZ уже предусматривает `tools/fetch_model.py`, поэтому скрипт остаётся **dev-инструментом**:
  `tools/export_model.py` качает `.pt` из ассетов Ultralytics, экспортирует профили D1, считает
  SHA-256 и печатает готовую строку для `manifest.json`.
- Releases нашего репозитория — единственный источник, который мы версионируем и не зависим
  от чужих аккаунтов/HF-токенов; HF-зеркало может быть добавлено как резервный URL в манифест
  без правок кода.
- `.pt` мы **не распространяем**. Наш релиз — AGPL-3.0, мы публикуем исходники приложения и
  скрипт экспорта, веса (AGPL-3.0, Ultralytics) распространяются как ассет релиза с явным
  notice в README и About. Пользователь вправе подключить собственную .onnx — путь остаётся
  поддерживаемым сценарием, а не «отладочной лазейкой».

## 6. D6 — Дефолтный лимит кэша

**Решение: 8 ГБ**, LRU-вытеснение по размеру, путь по умолчанию
`%LocalAppData%\ParallelFinder\cache\`, смена пути на другой диск в настройках; предупреждение,
если на выбранном диске меньше 2 ГБ свободного места (ниже 1 ГБ — анализ не стартует).

Оценка на 3-часовом проекте (10 800 с, 30 fps, ~324 тыс. кадров, окно 1.0 с / страйд 0.25 с ⇒
~40 тыс. окон):

| Компонент | Оценка |
|---|---|
| Треки и keypoints (доминант, квантизация fp16/int8) | 40–90 МБ |
| Дескрипторы движения + HNSW-индекс (≈2.2 КБ/окно × 40 тыс. × 1.3) | ~120 МБ |
| Превью сцен и моментов (WebP 320×180 ≈15 КБ × ~2 000) | ~30 МБ |
| **Итого типично** | **≈0.3 ГБ** |
| Худший случай (fp32, несколько персонажей, много превью, несколько файлов) | 1.0–1.5 ГБ |

Обоснование дефолта: 8 ГБ — это запас ×5–8 от типичного проекта и ×20 от оценки худшего
случая, которого достаточно, чтобы библиотека из ~20–25 часов разного материала
переключалась без пересчёта; при этом на типичном SSD это <1% объёма. Ниже 2 ГБ начинаются
промахи кэша при обычной работе, и пользователь платит за них минутами GPU-времени —
это худший обмен, чем 8 ГБ диска. Лимит сменный, включая меньшие значения: кэш
восстанавливается пересчётом, потери данных нет.

Уточнение: после стадии 4 замеряется реальный размер кэша на 3-часовом проекте и
записывается в этот раздел; если расхождение с оценкой >2×, дефолт пересматривается.

## 7. D7 — Таблица 9 слайдеров → `MotionMatcherParams`

Порядок и подписи слайдеров — как в ТЗ п.3. Поля — часть контракта `pfcore::MotionMatcherParams`
(стадия 3b обязана совпасть с этой таблицей; расхождение — ошибка стадии).

| # | Слайдер | Поле | Диапазон | Шаг | Дефолт | Семантика |
|---|---|---|---|---|---|---|
| 1 | Порог схожести | `similarityThreshold` | 0.50–0.99 | 0.01 | **0.85** | минимальное `S` (раздел 4), при котором пара вообще предлагается |
| 2 | Порог кандидата | `candidateThreshold` | 0.10–0.95 | 0.05 | **0.55** | минимум ANN-близости в HNSW-префильтре: ниже — окно не доходит до точного DTW. Ниже значение = выше recall и больше времени |
| 3 | Минимальный зазор между повторами | `minRepeatGapSec` | 0.5–60 с | 0.5 | **6.0** | два срабатывания одного и того же движения ближе этого интервала считаются одним повтором (совпадает с прототипом: «Мин. интервал повторов 6c») |
| 4 | Зазор для одного видео | `sameFileGapSec` | 0.0–30 с | 0.5 | **2.0** | минимальное расстояние между началами моментов A и B, если оба из одного файла (защита от тривиального самосовпадения соседних окон) |
| 5 | Зазор для разных видео | `crossFileGapSec` | 0.0–30 с | 0.5 | **0.0** | то же для пары из разных файлов: самоналожения там невозможны, ограничение по умолчанию снято |
| 6 | Окно дубликатов | `duplicateWindowSec` | 0.0–10 с | 0.25 | **1.5** | две пары дублируют друг друга, если |Δ начала| ≤ окна и по A, и по B; остаётся пара с большим `S` (дедуп вместо «одного результата на клип», как требует ТЗ п.3) |
| 7 | Коэффициент шума | `noiseFactor` | 0.0–3.0 | 0.1 | **1.0** | множитель оценки шумового пола: `d' = max(0, d − noiseFactor · d_noise)`, где `d_noise` — медианная покадровая девиация внутри окна. Убирает ненулевой базовый «шум» позы на статике, чтобы сходство было сравнимо между спокойными и тряскими фрагментами |

влияют на то, какие пары находятся, слайдер 8 — только на объём вывода.

## 8. Сопутствующие решения (не покрыты п.10, но блокируют 3b/4)

| Вопрос | Решение | Обоснование |
|---|---|---|
| Длина окна движения | `windowSeconds` = **1.0 с** (диапазон 0.4–3.0) | вмещает полный цикл жеста/удара/поворота; короче — теряется контекст, длиннее — растёт цена DTW и размывается граница клипа |
| Страйд окна | `strideSeconds` = **0.25 с** (0.1–1.0), округление до кадров | 4 окна/с дают ~40 тыс. окон на 3 часа: точность границ приемлема, объём работы для HNSW+DTW по силам |
| Минимальная длина клипа-кандидата | 0.5 с = минимум 15 кадров при 30 fps (та же константа, что «минимальное окно») | окно движения должно целиком помещаться в сцену |
| Полоса Сакое-Чиба | `sakoeChibaRatio` = **0.10** от длины окна, минимум 2 шага (диапазон 0.05–0.25) | допускает локальный сдвиг темпа ±10% без превращения DTW в полный O(N²); параметр в настройках, не среди 9 слайдеров (ТЗ п.3: «ширина — настраиваемый параметр») |
| Ранжирование результатов | по `S` убыв., при равенстве — по большему суммарному времени в кадре, затем по времени начала A | детерминированный порядок нужен и для UI, и для `expected.json` в тестах |
| Порог F1 приёмки | синтетические фикстуры **≥ 0.90**, реальные видеофикстуры **≥ 0.60**, регресс к предыдущему замеру не хуже 0.02 | синтетика геометрически точная, планка жёсткая; на реальном материале ground truth субъективен (границы клипов допускают ±0.3 с), поэтому 0.60 — уже рабочее качество, а не компромисс. Оба порога фиксируются в тестах стадии 3b, не «на глаз» |
| Параметры позы (опции прототипа) | `normalizeScale` = вкл, `mirrorPoses` = вкл, `useBodyPartWeights` = выкл | совпадает с состоянием чекбоксов в прототипе; веса частей тела по умолчанию выключены, чтобы базовая формула была проще и её можно было калибровать |
| Где живут пороги SceneDetector | `settings.json` + Settings-диалог, тултипы; не среди 9 слайдеров | ТЗ п.3 требует именно 9 слайдеров анализа; вынос scene-порога в отдельный слайдер — изменение ТЗ и требует подтверждения владельца |
| Кэш-ключ сессии ORT | модель + профиль + провайдер | две модели в одном профиле и один и тот же вес в разных профилях — разные сессии (см. D1) |
| Версия-агностичная загрузка ORT | без изменений: `LoadLibraryW` + `OrtGetApiBase` (стадия 0) | уже реализовано и покрыто тестами в скелете |

## 9. Загрузка ONNX Runtime и выбор провайдера (уточнено в стадии 1)

ТЗ п.2 требовало «уточнить в стадии 1» версионно-агностичную загрузку ORT. Что выяснилось на
живой машине и как это решено:

- **Заголовки и DLL могут быть из разных версий.** На машине разработчика заголовки ONNX Runtime
  1.26 (`ORT_API_VERSION 26`), а загружаемая `onnxruntime.dll` — 1.17.1 (API до v17). Поэтому
  `OrtGetApiBase()->GetApi()` пробегает версии **снизу вверх** от 12 до `ORT_API_VERSION` и берёт
  максимальную поддерживаемую. Вверх, а не вниз, потому что `GetApi()` пишет в stderr строку на
  каждую неподдерживаемую версию, а мы эту мешанину версий видим регулярно. Структура `OrtApi`
  только дописывается в конец, поэтому полученная для версии N структура безопасна для всех
  функций, существующих в N.
- **Провайдеры нельзя привязывать по имени.** `SessionOptionsAppendExecutionProvider` (generic, с
  ORT 1.12) знает только фиксированный список (`OPENVINO`, `SNPE`, `XNNPACK`, `QNN`, `WEBNN`,
  `AZURE`) и **отклоняет** `CUDAExecutionProvider` / `DmlExecutionProvider` /
  `TensorrtExecutionProvider` с «Unknown provider name». Два рабочих пути:
  1. **ORT ≥ 1.22: EP-device API** — `GetEpDevices` → выбор `OrtEpDevice` по `EpDevice_EpName` →
     `SessionOptionsAppendExecutionProvider_V2`. Оба помечены «\since Version 1.22», это
     документированный путь для актуальных GPU-пакетов.
  2. **ORT 1.12–1.21: классические экспортируемые функции**
     `OrtSessionOptionsAppendExecutionProvider_CUDA|DML|TensorRT(options, device_id)`, которые
     берутся через `GetProcAddress` — per-EP заголовки по-прежнему не нужны.
  Устаревшие варианты `OrtApi::..._CUDA(const OrtCUDAProviderOptions*)` сознательно не
  используются: их структуры привязывают нас к конкретному ABI рантайма без выигрыша.
- **«Доступен» = сессию удалось создать.** `GetAvailableProviders` по документации не гарантирует,
  что провайдер инициализируется, поэтому проба создаёт настоящую сессию на встроенной модели
  (Identity над `float32 [1,2]`, генерируется кодом, а не бинарной фикстурой — модели в
  репозиторий не коммитятся). Если провайдер не работает, в бейдже показывается текст ошибки
  рантайма, а не «недоступен» без объяснения.
- **Проверено на реальной машине:** ORT 1.17.1, цепочка TensorRT → CUDA → **DML (доступен)** → CPU;
  автоопределение выбрало DirectML на NVIDIA RTX 5070. CUDA и TensorRT недоступны потому, что
  в рантайме из MSYS2 нет GPU-провайдеров — это работа стадии 6 (GPU-бандл), и до неё
  `auto` в приоритете DML соответствует ТЗ.
- **Переопределение пути к рантайму:** переменная окружения `PF_ORT_DLL` позволяет указать
  `onnxruntime.dll` из `D:\PF_CUDA` без правки `PATH`; без неё поиск идёт штатно (папка exe, потом
  `PATH`), что и нужно портативному релизу.

Кэш сессий ключуется парой модель + провайдер + устройство + профиль модели (D1), поэтому
профили `b1`/`b8` никогда не переиспользуют одну сессию. Вытеснение LRU не выдёргивает сессию у
того, кто уже держит её в работе: дескриптор владеет записью кэша.
