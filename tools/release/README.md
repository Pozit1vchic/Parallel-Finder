# Подготовка Windows-сборок

## Локальные ZIP и установщик

Из корня репозитория в PowerShell 7:

```powershell
./tools/release/build-windows.ps1
```

Пути к MSYS2 UCRT64, базовым моделям и Inno Setup задаются параметрами скрипта.
Скрипт сначала собирает приложение и запускает CTest, затем создаёт новую staging-папку и артефакты в `release/<ReleaseTag>-<id>`. Существующие папки не удаляет. Номер сборки виден в заголовке окна, чтобы отличить новую сборку от старой. Пакет содержит CPU ONNX Runtime, Qt, FFmpeg и базовые модели; NVIDIA runtime не включается. Путь к Qt-плагинам для тестов задаётся временно; после тестов окружение Qt восстанавливается, а после завершения скрипта восстанавливается PATH текущего процесса.

Для другого номера передайте `-ReleaseTag '<номер>'`: версия приложения, установщика и имена архивов будут согласованы.

**Перед публичной публикацией** закрыть ограничения [предрелизного аудита](../../docs/release-audit.md), в том числе обязательства по лицензиям/соответствующим исходникам. Локальная RC-сборка не равна готовому стабильному выпуску.

ZIP распаковывается целиком; installer устанавливает в пользовательскую папку без администратора. Portable использует пользовательское хранилище настроек и не обещает полную изоляцию от AppData.

## Публикация обновления приложения

В один GitHub Release приложения загрузите Portable ZIP, installer, Source ZIP, `SHA256SUMS.txt`, **`update.json` и `update.json.sig`** из одной сборки. Последние два файла обязательны для обновления: SHA256SUMS сам по себе не подтверждает подлинность пакета. Не редактируйте подписанный JSON вручную без повторной подписи доверенным ключом.

Канал Stable показывает обычные опубликованные релизы GitHub (`prerelease=false`), в том числе теги с `rc`, если автор опубликовал их обычным релизом. Beta показывает и обычные релизы, и Pre-release. Draft не показывается в обоих каналах. Клиенты RC17.1/RC18 до исправления дополнительно исключали RC-теги из Stable — в них для такого выпуска требуется Beta.

Для клиентов RC17.1 версия в подписанном манифесте должна **буквально совпадать** с тегом GitHub, включая префикс `v`. Новые клиенты сравнивают версии по SemVer. Для уже опубликованного `v0.1.0-rc.18` локальные `update.json` и `update.json.sig` подготовлены с этим префиксом и повторно подписаны; Portable ZIP менять не требуется. При их загрузке замените также `SHA256SUMS.txt` актуальным файлом.

## Отдельные релизы данных

- Модели: тег **v0.1.0-models**, assets ONNX и manifest.json. URL внутри manifest тоже должны указывать на этот тег.
- GPU runtime: тег **runtime-v1**, providers.json и проверенные ZIP. См. [инструкцию](../../docs/runtime-distribution.md).
- Приложение: отдельный тег; не смешивать его latest со ссылками моделей/runtime.

Экспортёр tools/model_export/export_pose_release.py теперь использует закреплённый model-тег по умолчанию. Старые локальные manifest с releases/latest необходимо пересоздать до публикации.

## Публикация моделей

```powershell
./tools/release/publish-model-release.ps1 -Tag v0.1.0-models
```

Требуется GitHub CLI и авторизация владельца. Скрипт проверяет хэши и размеры; авторизация не хранится в Git. Исходные .pt и крупные ONNX не коммитятся. Обычный git push публикует исходники, но не создаёт Release assets.

Успешная упаковка удаляет только свои временные package/source-папки из build; готовые релизы и основной каталог компиляции сохраняются. Для диагностики staging можно оставить флагом `-KeepStaging`. Перед тестами скрипт разворачивает нужные зависимости, поэтому чистый build больше не зависит от файлов прежней сборки.
